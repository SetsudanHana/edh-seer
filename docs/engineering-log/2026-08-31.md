|---|---|
| type-line land count, which `build.ts` scores and reports | **38** |

| `landRec.target`, already discounted for those MDFCs | **33** |

pair, so every deck running an MDFC had been docked build score for cards it owns.

**`deck-math.ts` was already internally consistent** — it pairs `rec.actual` with `rec.target`, and
`BuildBenchmarks.tsx` rendered the reconciliation: *"34 (38 with MDFCs) · 4 modal DFCs priced as

### The ruling, and why it went against the published regression

Three conventions were measured across the **55 of 71 calibration decks that run a land-back MDFC**,
as delta between the deck's land count and its target:

| convention | mean delta | mean \|delta\| | outside ±3 |
|---|---|---|---|
| as it was — discount applied, card still counted | **+1.56** | 2.58 | 17/55 (15 high, 2 low) |
| all-Karsten — count it as a spell, keep the discount | **−1.40** | 2.53 | 16/55 (3 high, **13 low**) |
| **an MDFC is a land, no discount** | **−0.36** | 2.18 | **12/55 (6 high, 6 low)** |

**The shipped arm wins on all three, and it is the only one whose misses are symmetric.** The
all-Karsten arm reading real decks 1.4 lands SHORT is the substantive finding: that is the signature
of players already treating these as lands and running fewer real ones to compensate, which is
exactly the owner's argument — *"typically you play mdfcs as a land primarily and then you can use
the spell if you have enough nonmdfc lands"*. **The first recommendation from this seat was the
all-Karsten arm, and the measurement reversed it.**

CHECKED, NOT ASSUMED: every tapped classification across the 71 decks is the always-tapped cycle —
12 distinct cards, all reading *"This land enters tapped."* (Malakir Mire, Khalni Territory, Valakut
Stoneforge, Kazuul's Cliffs, Silundi Isle …). The pay-3-life rares all classify untapped, so
`mdfcLandBack` already draws the line the owner's second point named.

**COST, NAMED RATHER THAN HIDDEN:** 0.74-vs-0.38 was the model's way of saying a tapped land-back is
worth half an untapped one, and counting both at 1.0 throws that away. `mdfcUntapped`/`mdfcTapped`
are still reported so a refinement has its input; inventing a third coefficient to split the
difference would be fitting to 55 decks.

### The other half of the double count

A card counted as a land also has to leave the pool that sets `avgManaValue` — the regression's
dominant term — or its mana value pushes the target back up by part of what the count just gained.
Small (~0.03 across the calibration decks) and wrong in principle; it has its own test. It is also
why five decks' targets moved DOWN: their MDFCs are expensive, so the spell pool got cheaper.

## Mobile is its own round now, and the graph is absent by construction

Owner, from a phone: *"I can not see the graph"*, and *"on cards list there is top item on the list
cut."*

The first is not a rendering bug. `ReportTabs.tsx:126` branches on `useIsNarrow()` and renders

the cutoff at Tailwind's `sm`, 639px, **so every phone in portrait gets the list and never the

specifically because at 390px its five tabs run 32px past the row. Step one is measuring the strip's
real height against the 33 the header assumes; the fix deletes the magic number rather than re-tuning
it.

## The app was installable the whole time and never said so

Owner, from an Android phone: *"if I open the website on android phone it does not appear to be
'installable'."*

**Everything Chrome requires was present and working on the live site**, checked end to end against
`https://edhseer.pages.dev/` rather than against the source: HTTPS and a secure context; the manifest
served 200 as `application/manifest+json` with `id` · `name` · `short_name` · `start_url` ·
`display: standalone`; icons at 192, 512 and 512-maskable, each a real PNG at the size it claims; a
service worker **registered, `activated` and controlling the page**, with a `fetch` handler that
falls back to a precached `/`; and no `beforeinstallprompt` handler anywhere calling
`preventDefault()` on the browser's own affordance.

**So the checklist was never the problem. Chrome on Android removed the automatic install banner**,
which leaves installing in the browser's own menu — and a reader who does not go looking there cannot
tell an installable app from one that refuses to install. `pwa.test.ts` had said the failure mode out
loud when it was written: *"the browser simply does not offer to install, and nothing on screen says
why."* It was right about the mechanism and wrong about the cause.

`InstallButton.tsx` handles `beforeinstallprompt`, portals a fourth item into the static header's
nav, and calls `prompt()` on click. **THE EVENT FIRING IS THE WHOLE GATE**, which is what keeps the
button honest: it never renders on iOS Safari (no such event — Add to Home Screen is a Share-sheet
item, and the `apple-*` tags already decide how it looks), never in an already-installed window, and
never on a browser that has declined to offer. There is deliberately no `display-mode: standalone`
check beside it, because Chrome does not fire the event once installed and a second condition testing
the same fact is decoration. The event is spent on click — a second `prompt()` throws — so the button
goes as soon as it is pressed, whatever the reader then chooses.

Verified in a browser rather than from the tests alone: the button lands inside the real
`.site-nav`, and its computed font family, size, weight, letter-spacing, text-transform and colour
all equal the nav links' — JetBrains Mono, 11px, 500, 1.1px, uppercase, `--muted`. At a 390px
viewport the nav does not overflow (scrollWidth 326 = clientWidth 326) and the body gains no
horizontal scroll. Suite 2,827, typecheck clean.

## Back left the site, and four buttons left the screen

Two owner reports from the deployed site, both consequences of the share-link work landing.

### There was no way back

*"after we added the url there is no easy way to go back from the analysis."*

`analyse` wrote the share hash with `replaceState`, and the comment beside it named a real reason —
re-analysing should not fill the back button with near-identical entries. **The consequence nobody
followed through was that the FIRST analysis created no entry either**, so the reader went from a
paste box to a full report with the browser recording that nothing had happened, and Back left the
site entirely.

The rule is now about which analysis it is: **push the first, replace the rest.** Pushing only when
the URL does not already carry a deck keeps both properties — one entry for "I analysed something",
none for the re-runs, and none for opening a shared link, whose hash is already there on load. A
`popstate` listener makes the entry mean something when you reach it: a deck hash re-opens that
analysis, a clean URL leaves the report for the paste box.

**THE DECKLIST SURVIVES A BACK.** "Out of the report" is what was asked for, not "start over" —
landing on an empty box would throw away the list the reader just pasted, and the report is one click
away again. Verified in a browser at 390px: Back clears the hash, drops the report, restores the
paste box **with all 90 lines still in it**.

### Four buttons, 76px off-screen

*"on mobile because we have a lot of buttons after analysis the overflow outside of the screen now."*

Measured before touching anything, on a 390px viewport with the example deck analysed: the collapsed
bar's button group (Copy link · Copy decklist · Edit · Re-analyze) ran **409px wide, its right edge at
465.6px, and `document.body.scrollWidth` 466 against a 390 client width** — 76px of the row off-screen,
taking the whole page's horizontal scroll with it.

**The cause was `shrink-0` on the button group**: correct on a desktop, where it stops the buttons
squashing before the summary truncates, and an instruction never to fit on a phone. Wrapping is what
a phone has room for, and `justify-between` still puts the summary and the buttons on opposite ends
whenever one line is enough.

**After: `bodyScrollWidth` 466 → 390, horizontal overflow false, and the row wraps** — three buttons
on the first line, Re-analyze on the second, every right edge inside the viewport. Suite 2,829.

This is the second finding in a row where a desktop-correct rule was a mobile-fatal one, which is the
whole argument for section R existing.

## The origin moves to edhseer.cards

Owner's choice between `edhseer.xyz` (cheapest) and `edhseer.cards`. **`.cards` on three grounds, in
the order they bite**: the domain is *inside* the Moxfield and Archidekt access requests about to be
sent, and a `.xyz` origin reads as a weekend throwaway to whoever triages them; `.cards` is
semantically true for a card-game tool; and the SEO work just shipped under one origin, so the moment
to only ever have one domain is before the first is indexed. **A CORS allowlist entry is per-origin,
so the domain had to be settled before the requests go out, not after.**

**THE COMMENT IN `index.html` WAS WRONG AND WOULD HAVE COST A HALF-APPLIED RENAME.** It read *"THE
ONE ABSOLUTE URL IN THE APP … the one string to change on the day a custom domain replaces the
pages.dev one."* The origin appears **eleven times across four source files** — five in
`index.html`, three in `how-it-works/index.html`, two in `public/sitemap.xml`, one in
`public/robots.txt`. The comment now says so, and says what actually keeps them honest.

**`seo.test.ts` already derived the origin from the canonical tag**, so robots, the sitemap and the
how-it-works canonical all moved with the page rather than failing against it — that design paid for
itself here. **It had one hole: the "every absolute URL agrees" assertion ran on `index.html` alone**,
so `how-it-works`'s `og:url` and `og:image` were unchecked and a rename applied to one file would
have left them pointing at the old origin with the suite green and every shared link from that page
resolving elsewhere. A test now asserts the second page's absolutes against the same canonical, with
a floor so an empty match list cannot pass it vacuously. **Mutation-proven before the rename: with
`index.html` alone changed, four tests fail** — the new one plus robots, sitemap and the
how-it-works canonical.

`dist/` is gitignored build output and was deliberately left alone; `npm run deploy` regenerates it.
